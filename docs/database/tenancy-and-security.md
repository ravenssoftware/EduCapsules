# Tenant Isolation, Soft Deletion, and Audit — Phase 3 Implementation

Companion to `schema-overview.md`. Covers the SRS's tenant-isolation, soft-deletion, and audit requirements as actually implemented, and states plainly where the database layer cannot carry the whole requirement by itself.

## 1. Tenant isolation (GEN-019, DB-001, DB-011, DB-012, ORG-002)

Every organization-scoped table carries `organization_id`, and every cross-table reference **within** a tenant is a **composite foreign key** on `(organization_id, <parent>_id)`, not a plain FK on the id alone (DB-011). Concretely:

- Every scoped parent table declares `UNIQUE(organization_id, id)` in addition to its normal primary key on `id` alone — `id` is already globally unique; the composite unique index exists *only* so child tables have something to composite-FK into.
- Every child table's FK to that parent is declared as `FOREIGN KEY (organization_id, parent_id) REFERENCES parent(organization_id, id)`, e.g. `classrooms(organization_id, academic_period_id) → academic_periods(organization_id, id)`.

**Effect:** a row that references a real, valid parent id but tags it with the *wrong* `organization_id` is a foreign-key constraint violation at the database layer — not merely an application bug that a missing authorization check could let through. This is verified for real, not just asserted in a diagram: `packages/db/src/schema/db-behavior-scenarios.ts`'s "blocks a cross-tenant composite foreign key" test creates two organizations, inserts an `academic_periods` row under organization A, and asserts that a `classrooms` row in organization B pointing at that period id is rejected by both SQLite and PostgreSQL, while the same insert scoped correctly to organization A succeeds.

**What this does *not* mean:** a foreign key is not authorization. This schema-level constraint stops a *structurally* cross-tenant write; it says nothing about whether the acting user is allowed to write to organization A at all. The centralized authorization architecture (`docs/architecture/auth.md`) remains the actual authorization boundary — every repository method still must inject `organization_id` from the authenticated request context, never from client input, per `docs/architecture/database.md` §2. The database constraint is a second, independent layer behind that check, not a replacement for it.

`user_role_assignments.scope_id` and the two polymorphic pairs (`memberships.container_type/container_id`, `course_audiences.target_type/target_id`) cannot carry a composite FK — a polymorphic reference has no single target table by construction. Where the SRS enumerates the legal target-type values, a CHECK constraint pins that enumeration (see `schema-overview.md` §6); the actual referenced row's existence and organization match must be validated at the application/service layer for these specific columns. This is exactly the gap the Phase 3 instructions ask to be named rather than silently patched over: it is named here.

**Closed for `memberships.container_id` and `course_audiences.target_id` in Phase 6** — `apps/api/src/modules/academic-structure/service.ts`'s `resolveContainerOrThrow()` (used by `addMembership()` and `addCourseAudience()`) looks the referenced Classroom/Group up by `(organization_id, id)` before the row is written, rejecting a nonexistent or cross-organization reference with `404 not_found`; see `docs/academic-structure/academic-structure.md` §4.4. `user_role_assignments.scope_id`'s equivalent validation remains Phase 5's own concern (the authz pipeline's scope-containment resolution already walks it) and is unaffected by this.

## 2. Soft deletion (DB-003, DB-017)

Tables holding user-visible academic content (`users`, `classrooms`, `groups`, `subjects`, `courses`) carry a nullable `deleted_at`. Setting it is the application's deletion path; the row is never physically removed by that path. The database backs this up structurally: because every FK uses the default `NO ACTION`/`RESTRICT` behavior (no `ON DELETE CASCADE` is declared anywhere in this schema), a hard `DELETE` against a row that still has children referencing it fails at the database layer — verified by the "blocks hard-deleting a referenced parent" test in `db-behavior-scenarios.ts`, which soft-deletes a classroom, confirms the row and its `deleted_at` are still readable, then confirms a hard `DELETE` against that same classroom is rejected while a `groups` row still references it.

`users.deleted_at` is reserved for the future erasure pipeline (§44, Phase 25) and is unused by anything in Phase 3.

## 3. Audit log — append-only (DB-004, AUD-001/002/004/005)

`audit_log` is structurally append-only in the sense that nothing in this codebase issues `UPDATE`/`DELETE` against it, and its own columns never include a "last edited" field. True database-privilege-level enforcement — the application's runtime role having no `UPDATE`/`DELETE` grant on this table at all — is dialect-dependent and is flagged here explicitly rather than silently varying by engine:

- **PostgreSQL** (`packages/db/migrations/postgres/0001_audit_log_append_only.sql`): a real `REVOKE UPDATE, DELETE ON TABLE audit_log FROM <role>` is the correct mechanism, and Postgres has the role system to support it. The migration is written as a guarded no-op (it only revokes from a role if that role already exists) because the actual deployment role name and provisioning are a later, not-yet-made deployment/ops decision — Phase 3 does not invent one. **Follow-up required in the deployment phase:** provision a distinct, lower-privileged runtime role for the backend (separate from the migration/owner role) and either name it to match this migration or add the matching `REVOKE` at that time.
- **SQLite / Cloudflare D1** (`packages/db/migrations/sqlite/0001_audit_log_append_only.sql`): there is no database-level user/privilege system on this dialect at all — no `GRANT`/`REVOKE`, no roles. A trigger that raises on `UPDATE`/`DELETE` was considered and deliberately rejected, since Phase 3 instructions explicitly forbid business logic in database triggers and a mutation-blocking trigger is exactly that kind of vendor-specific procedural logic. **Decision:** on this dialect, append-only enforcement for `audit_log` must be implemented at the application/service data-access layer — the data-access module must never issue `UPDATE`/`DELETE` against this table, regardless of engine. This is a documented gap, not a silently weakened requirement.

`audit_log` never stores credentials, access tokens, or other secrets — only `actor_user_id`/`actor_role`, the action name, a polymorphic `target_type`/`target_id`, opaque before/after references, an `ip_hash` (never a raw IP), and an optional `login_session_id`/`reason`.

**`security_events`** (added Phase 4, DB-004's second named append-only table alongside `audit_log`) gets the exact same treatment — `packages/db/migrations/postgres/0004_security_events_append_only.sql` mirrors the guarded PostgreSQL `REVOKE`, and `packages/db/migrations/sqlite/0004_security_events_append_only.sql` carries the same documented SQLite/D1 gap. It is narrower in purpose than `audit_log`: only the abuse/threat-signal subset of Table 36.2's Authentication events that API-018 specifically requires (`RATE_LIMIT_EXCEEDED`, `LOGIN_BRUTE_FORCE`, `ACCOUNT_LOCKED`, `TOKEN_REUSE_DETECTED`, `SUSPICIOUS_SESSION`) — ordinary authentication events (`LOGIN_SUCCESS`, `LOGIN_FAILED`, `LOGOUT`, `MFA_SUCCESS`, etc.) go to `audit_log` instead, per `docs/auth/authentication.md`. It is also the one table in this schema whose `organization_id` is nullable by design: some events (an anonymous rate-limit trip against the public login endpoint before any credential is even checked) have no resolvable tenant yet.

## 4. Seed data policy (never a source of implied product requirements)

`packages/db/src/seed/data.ts` has two tiers:

- **System roles** (`systemRoleRows()`) — the five roles GEN-006 names (STUDENT, TEACHER, ASSISTANT, PARENT, ADMIN), fixed pre-generated UUIDv7 ids, `organization_id` null. This is safe to seed in every environment, including production, because it is a fixed fact the SRS itself states, not product/business data.
- **Dev sample data** (`devSampleData()`) — a synthetic organization, two users, one classroom/group/subject/course. Every name and identifier is fictional; every email uses the `example.test` domain (RFC 2606, reserved specifically so it can never resolve to a real inbox). Gated behind an explicit `--dev` CLI flag on both `db:seed:sqlite:dev`/`db:seed:postgres:dev`, and hard-refused (non-zero exit, no rows written) whenever `NODE_ENV=production` regardless of the flag.

Both seed paths are deterministic and idempotent: every row uses a fixed, pre-generated UUIDv7 rather than one generated fresh per run, and every insert uses `onConflictDoNothing()` — re-running a seed script against an already-seeded database is a safe no-op, not a duplicate-row error. Verified by the "is idempotent when the same role seed row is inserted twice" test.
